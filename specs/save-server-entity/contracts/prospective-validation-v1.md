# Prospective repository validation contract v1

Status: NORMATIVE ARCHITECTURE CONTRACT.

Source: approved feature specification v2, FR-SAVE-018/026,
VR-SAVE-004/005/011, QR-SAVE-002, and AC-SAVE-011/012.

## 1. Shared engine

`lint`, pre-write `apply`, and prospective `save` validation call one repository
validation engine. The engine's input is a `RepositoryView`, not an implicit
filesystem scan. Its observable order remains:

```text
discover -> bounded read -> safe YAML parse -> closed schema and sidecar expansion
-> effective project -> natural semantics -> duplicate natural identities
-> complete graph references
```

Warnings remain a lint-only post-validation concern. Save does not emit or
persist warning data.

## 2. Repository view interface

Conceptual interface:

```text
trait RepositoryView {
    enumerate_yaml() -> ordered list<RepositoryRelativePath>;
    open_yaml(path) -> BoundedUtf8Bytes;
    open_sidecar(owner_yaml, relative_path) -> BoundedBytes;
    root_identity() -> RepositoryRootIdentity;
}
```

The interface returns values or typed layer errors. It exposes no raw OS error
or arbitrary string to the diagnostic renderer.

`DiskRepositoryView` preserves current deterministic discovery, exclusions,
open-then-fstat reads, symlink policy, containment, and resource budgets.

`OverlayRepositoryView` contains exactly:

- one canonical generated YAML byte sequence at its intended final relative
  path; and
- for Skill only, one exact main-content byte sequence at the derived adjacent
  relative path.

It wraps a disk view, never replaces a disk entry, and owns immutable bytes.
The final paths must have passed publication path validation before overlay
construction.

## 3. Merge and read behavior

YAML enumeration is the bytewise ordered union of disk YAML paths and the
generated YAML path. A duplicate path or duplicate natural identity is a
failure. Non-YAML Skill sidecar bytes are not declaration-discovery entries.

When parsing generated Skill YAML, `contentFrom` resolves only through the
overlay's exact adjacent sidecar entry. It receives the same relative path,
UTF-8, size, containment, and aggregate-content checks as a disk sidecar. The
expanded parsed declaration contains `spec.content` just as current lint does;
the emitted YAML remains unchanged with `spec.contentFrom`.

All other sidecar reads delegate to the disk view under the caller's inherited
`--follow-symlinks` policy. Generated final paths themselves never follow
symlinks.

## 4. Success and failure

Prospective validation succeeds only if the entire merged repository closure
passes. The returned target declaration must match the requested kind and exact
effective natural identity. Missing local dependencies fail `E_REFERENCE`,
exit 2, using only a canonical schema field path. Existing duplicate identity
at another path fails before publication.

No overlay operation writes, renames, creates, truncates, changes permissions,
or updates timestamps. Generated bytes are dropped on failure and passed as an
immutable `ArtifactSet` to publication only on success.

## 5. Equivalence evidence

Before implementation is accepted:

- every existing lint fixture must produce the same success/failure and
  diagnostic classification through `DiskRepositoryView`;
- materializing an overlay into an otherwise equivalent temporary repository
  and running disk lint must equal in-memory validation;
- sidecar absent/escape/symlink/UTF-8/size cases must match disk behavior;
- generated duplicate identities and missing references must fail without
  final files; and
- cancellation at every read/validation checkpoint must leave no output.
